Implementation Report · Hackathon Reference

Two OpenShift clusters, one wire that can't go down.

Substations, rail signalling, and grid control systems need a network that survives a single cable failure with zero lost packets - not a fast failover, an invisible one. That's what Parallel Redundancy Protocol (IEC 62439-3) is for: every frame goes out two independent paths at once, and the receiver just uses whichever copy arrives first. This report walks through building and proving that link between two independent single-node OpenShift clusters on KVM, including a real installer bug we found along the way and how we worked around it.

01

The mechanism

Each node gets exactly 3 NICs - one dedicated port per role, nothing doubled up. One carries normal cluster traffic; the other two are each a leg of the PRP link. The two PRP networks are otherwise unreachable from anywhere - no DHCP, no routing, no host IP - which is what keeps this a clean redundancy test instead of an accidental extra route into the cluster.

02

The installer bug (and why it took two attempts to isolate)

The Day-0 network config for prp0 is written once, in standard NMState YAML, and it is correct - it validates cleanly against the reference nmstatectl. It still doesn't work at first boot, on either OpenShift version we tried it on.

Attempt 1: schema-valid, but rejected for a real reason learned something

Giving the two PRP ports different MAC addresses seemed natural - they're different physical NICs. nmstate disagreed, and it was right to:

build-time validation → nmstatectl gc
NmstateError: InvalidArgument: HSR ports on interface prp0 cannot have different MAC addresses

prp0 is one logical identity presented out two ports - both have to answer to the same MAC. Fix: keep each vNIC's real hardware MAC unique (needed elsewhere, for udev-based interface renaming), and set a shared, made-up operational MAC only inside the nmstate config for those two ports. NetworkManager reprograms the MAC at bring-up time; this part works.

Attempt 2: valid config, broken translator real installer bug

With that fixed, the config validates and builds an ISO without complaint. The node boots, eth1/eth2 come up correctly with the shared MAC applied - and prp0 simply isn't there.

live shell → device doesn't exist
$ ip -d link show prp0
Device "prp0" does not exist.
journalctl → NetworkManager's own complaint
keyfile: load: ".../prp0.nmconnection":
  invalid connection: hsr:
  setting required for
  connection of type 'hsr'

The generated file has type=hsr but no [hsr] section at all. openshift-install embeds its own nmstate-to-NetworkManager translator, older and different from the one that validated the config, and it silently drops every HSR-specific field. Confirmed identically on OCP 4.19.45 and 5.0.0-rc.2 - a real gap between the validator and the serializer, not something fixable by editing the YAML further.

03

The fix: kubernetes-nmstate-operator, Day 2

The operator's handler runs the real nmstatectl directly on the node via a privileged pod - a completely different code path from the broken Day-0 serializer - and produces a correct keyfile every time.

One extra wrinkle on 5.0.0-rc.2 catalog gap, not our bug

kubernetes-nmstate-operator isn't in any of 5.0.0-rc.2's default catalogs yet - checked all three, all healthy, 85-261 packages each, the operator in none of them. Likely a pre-GA gap (5.0 jumped to Kubernetes v1.36; not everything's rebuilt against it yet). Workaround: point a second CatalogSource at the last 4.x index (v4.22), which still carries it - OLM on 5.0 resolves and installs it from there without complaint.

Try it yourself

  1. Deploy: ansible-playbook sno_playbook.yml (builds both VMs, boots them)
  2. Wait: openshift-install agent wait-for install-complete --dir=<install_dir>
  3. Per cluster: oc apply -f day2-manifests/*.yaml in numeric order, waiting for each CSV/DaemonSet before the next file
  4. Verify: ip -d link show prp0 should show proto 1 on both nodes
